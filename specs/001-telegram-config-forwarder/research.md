# تحقیق: سامانه خودکار جمع‌آوری و انتشار کانفیگ تلگرام

**تاریخ**: 2026-09-23
**مبنا**: `spec.md` + شفاف‌سازی‌های نشست 2026-09-23 (۵ تصمیم مصوب)

> **قانون زبان (الزامی)**: این فایل به **زبان فارسی** نوشته شده است. شناسه‌ها، مسیرها و نام‌های فنی انگلیسی باقی می‌مانند.

## ۱. روش دریافت منبع (Source Acquisition)

- **تصمیم**: اولویت اول، تطبیق منطق `fast_engine` + `TelegramParser` پروژه مرجع (`E:\antigravity_project`) پشت واسط `SourceProvider`؛ اولویت دوم، Telethon با اعتبار امن.
- **دلیل**: موتور سریع مرجع بدون مرورگر و بدون ورود کار می‌کند (فقط `httpx` + `BeautifulSoup` + `Pydantic`) و برای رانر GitHub سبک و مناسب است؛ شناسه عددی پست (`data-post`) دقیقاً همان مبنای تشخیص تازگی مصوب Q1 است؛ واسط انتزاعی، تعویض ارائه‌دهنده را بدون تغییر منطق کسب‌وکار ممکن می‌کند (اصل VII قانون اساسی).
- **جایگزین‌های بررسی‌شده**: موتور مرورگری Playwright مرجع (رد شد برای اجرای پیش‌فرض چون دانلود Chromium سنگین و کند است؛ فقط گزینه محلی باقی می‌ماند)؛ Telethon به‌عنوان مسیر اصلی (رد شد چون برای کانال عمومی به اعتبار نیاز ندارد و با اصل کمینه‌سازی اسرار ناسازگار است).

## ۲. یافته‌های قابل استفاده مجدد از پروژه مرجع

- **تصمیم**: اقتباس انتخاب‌گرهای `TelegramParser` (متن، زمان `time[datetime]`، رسانه، بازدید، واکنش، فوروارد، نظرسنجی، پیش‌نمایش لینک)، مدل‌های Pydantic، صفحه‌بندی با `before`، ابزار `clean_channel_username` و پشتیبانی پروکسی.
- **دلیل**: این اجزا در عمل آزموده شده‌اند، متن فارسی RTL را درست نگه می‌دارند و نگاشت مستقیم به مراحل Fetch/Parse خط لوله دارند.
- **جایگزین‌های بررسی‌شده**: بازنویسی کامل از صفر (رد شد چون اتلاف تلاش اثبات‌شده است)؛ کپی بدون واسط (رد شد چون انتخاب‌گرهای DOM شکننده‌اند و باید پشت واسط + آزمون قرارداد ایزوله شوند).
- **احتیاط ثبت‌شده**: پست سنجاق‌شده باید فیلتر شود (مورد خاص spec)؛ خرابی انتخاب‌گر باید خطای ایزوله یک منبع باشد نه توقف کل اجرا.

## ۳. ارسال به مقصد (Destination Sending)

- **تصمیم**: مسیر اصلی `BotApiSender` با HTTPS مستقیم به Bot API؛ مسیر جایگزین `TelethonSender` با `API_ID`/`API_HASH`/`SESSION_STRING` از متغیر محیطی؛ هر دو پشت واسط `DestinationSender` با امضای یکسان.
- **دلیل**: Bot API بدون نشست و بدون وابستگی سنگین است و برای ارسال ساده به کانال کافی است؛ Telethon برای شرایطی که توکن بات کافی نیست (محدودیت، نیاز به نشست کاربری) جایگزین می‌شود؛ واسط یکسان، تعویض مسیر را بدون تغییر منطق کسب‌وکار ممکن می‌کند.
- **جایگزین‌های بررسی‌شده**: فقط Telethon (رد شد چون نشست، مدیریت پیچیده‌تر و سطح دسترسی بالاتر می‌خواهد)؛ فقط Bot API بدون fallback (رد شد چون با اصل VII ناسازگار است).

## ۴. آزمون کانفیگ با Xray Core

- **تصمیم**: دانلود باینری پیش‌ساخته رسمی Xray از صفحه Releases گیت‌هاب (نسخه پین‌شده + راستی‌آزمایی چک‌سام) در گردش کار؛ اجرای Xray به‌صورت زیرفرایند با پیکربندی تولیدشده برای هر کانفیگ (outbound از روی لینک + inbound محلی) و سپس آزمون اتصال از طریق پروکسی محلی.
- **دلیل**: مخزن `XTLS/Xray-core` (Go، پروانه MPL-2.0) باینری آماده لینوکس دارد و نیازی به build در CI نیست؛ این روش سریع‌ترین و تکرارپذیرترین نصب است (جایگزین‌ها: ایمیج رسمی Docker `ghcr.io/xtls/xray-core` و build از سورس که کندترند).
- **جایگزین‌های بررسی‌شده**: کتابخانه‌های لفاف (مثل `libXray`) (رد شد چون پیچیدگی بیلد و نگهداشت بیشتر است)؛ build از سورس در هر اجرا (رد شد چون زمان‌بر و غیرضروری است).

## ۵. معنای latency و ping (تفکیک حیاتی)

- **تصمیم**: هیچ‌جا از ICMP ping استفاده نمی‌شود. «تاخیر» در کل سیستم یعنی **تاخیر اتصال application-level**: مدت زمان برقراری اتصال TCP + دریافت پاسخ HTTP از یک هدف استاندارد از طریق پروکسی محلی Xray (مثلاً `http://www.gstatic.com/generate_204`)، بر حسب میلی‌ثانیه. فیلدها `latency_ms` و `test_status` نامیده می‌شوند، نه `ping`.
- **دلیل**: مستندات رسمی GitHub تأیید می‌کند بسته‌های ICMP ورودی در تمام ماشین‌های مجازی Azure مسدود است و دستور ping/traceroute روی رانرها کار نمی‌کند؛ تنها سنجه قابل اتکا در این محیط، اتصال TCP/HTTP از طریق خود کانفیگ است که دقیقاً همان چیزی است که برای کاربر نهایی هم مهم است (کارایی مسیر پروکسی، نه reachability میزبان).
- **جایگزین‌های بررسی‌شده**: ping سیستمی (رد شد — در رانر مسدود است)؛ فقط برچسب موفق/ناموفق بدون عدد (رد شد چون spec در صورت موجود بودن، نمایش تاخیر را می‌خواهد).

## ۶. نگهداری وضعیت در رانر موقت (Persistence)

- **تصمیم**: فایل `state/state.json` در خود مخزن که در پایان اجرای موفق کامیت و push می‌شود (شامل آخرین شناسه هر منبع، هش کانفیگ‌های منتشرشده، وضعیت توزیع چرخشی و تاریخچه خلاصه)؛ اجرای هم‌زمان با `concurrency` انحصاری ممنوع می‌شود.
- **دلیل**: رانر GitHub موقت است و فایل‌سیستم بین اجراها نمی‌ماند؛ کامیت در مخزن ساده، قابل حسابرسی و بدون سرویس خارجی است و دقیقاً نیاز Idempotency را برآورده می‌کند.
- **جایگزین‌های بررسی‌شده**: cache اکشن‌ها (رد شد چون برای درستی رفتار قابل اتکا نیست و ممکن است پاک شود)؛ Artifacts (رد شد چون چرخه دانلود/آپلود دست‌وپاگیر است)؛ پایگاه خارجی (رد شد چون وابستگی و secret اضافه می‌خواهد).

## ۷. تشخیص موقعیت (Location)

- **تصمیم**: پیش‌فرض، پایگاه GeoIP آفلاین (MaxMind GeoLite2 همراه بسته) روی IP/hostname استخراج‌شده از کانفیگ؛ در صورت نبود پاسخ، مقدار جایگزین قابل تنظیم (`Unknown`)؛ سرویس API آنلاین فقط به‌عنوان گزینه غیرفعال.
- **دلیل**: آفلاین بودن یعنی بدون وابستگی شبکه اضافه و بدون افشای کانفیگ به سرویس ثالث؛ با رفتار افت تدریجی spec سازگار است.
- **جایگزین‌های بررسی‌شده**: API آنلاین موقعیت (رد شد برای پیش‌فرض چون وابستگی خارجی و تأخیر اضافه می‌کند).
- **دریافت پایگاه**: دانلود `GeoLite2-City.mmdb` با `MAXMIND_LICENSE_KEY` از Secret در گردش کار و کش بین اجراها؛ جایگزین بررسی‌شده (کامیت فایل ~۶۰ مگابایتی در مخزن) رد شد چون حجم مخزن و به‌روزرسانی را سنگین می‌کند.

## ۸. زمان‌بندی و اجرای گردش کار

- **تصمیم**: `cron: '0 */3 * * *'` (هر ۳ ساعت) + `workflow_dispatch` برای اجرای دستی؛ `concurrency` انحصاری بدون لغو اجرای در حال انجام؛ خرابی جزئی (یک منبع/کانفیگ) باعث fail شدن کل job نمی‌شود مگر آستانه بحرانی.
- **دلیل**: دقیقاً معادل FR-022/FR-023 و اصل XI قانون اساسی است؛ انحصار، شرط لازم Idempotency در برابر اجراهای هم‌زمان است.

## ۹. پشته فنی و مدل هم‌زمانی

- **تصمیم**: Python 3.12 (حداقل 3.11)؛ وابستگی‌های `httpx`، `beautifulsoup4`، `pydantic>=2`، `telethon`، `pyyaml`، `geoip2`؛ آزمون با `pytest` + `pytest-asyncio`؛ پردازش منابع به‌صورت ناهمگام با حد هم‌زمانی قابل تنظیم و ایزوله‌سازی خطای هر منبع.
- **دلیل**: هم‌خوان با پروژه مرجع (نصب سریع روی `ubuntu-latest`)؛ ناهمگامی، توان عملیاتی چندمنبعی را بدون پیچیدگی multi-process می‌دهد؛ خطای یک منبع، بقیه را متوقف نمی‌کند (FR-024).
- **جایگزین‌های بررسی‌شده**: پردازش کاملاً ترتیبی (رد شد چون با رشد منابع کند می‌شود)؛ multi-processing (رد شد چون پیچیدگی بی‌مورد برای این حجم کار است).

## ۱۰. کارایی تست (حذف تست تکراری)

- **تصمیم**: ترتیب خط لوله طوری است که حذف تکراری (تطبیق دقیق رشته، مصوب Q5) **قبل** از تست Xray انجام می‌شود؛ نتیجه تست سراسری یک‌بار محاسبه و بین همه مقصدها مشترک استفاده می‌شود (مصوب Q4).
- **دلیل**: هر اجرای Xray پرهزینه است (spawn فرایند + handshake شبکه)؛ با این ترتیب هیچ کانفیگ تکراری تست نمی‌شود و هیچ کانفیگی دو بار تست نمی‌شود — مستقیم در جهت اصل کارایی plan.
