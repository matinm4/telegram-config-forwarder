## خلاصه

سامانه‌ای خودکار که کانال‌های منبع تلگرام را با اولویت اسکرپ پیش‌نمایش عمومی (تطبیق موتور سریع پروژه مرجع) و مسیر دوم Telethon می‌خواند، کانفیگ‌ها را استخراج، حذف‌تکراری دقیق، پالایش ترکیبی و قالب‌بندی می‌کند، در صورت فعال بودن موقعیت (GeoIP آفلاین) و تست اتصال (Xray با تاخیر application-level) را اعمال می‌کند، نتیجه را با توزیع چرخشی بین مقصدها (ارسال اصلی Bot API، جایگزین Telethon) تقسیم می‌کند و وضعیت را در خود مخزن نگه می‌دارد؛ کل چرخه هر ۳ ساعت در GitHub Actions بدون وابستگی به رایانه شخصی اجرا می‌شود.

## زمینه فنی

**زبان/نسخه**: Python 3.12 (حداقل پشتیبانی 3.11)

**وابستگی‌های اصلی**: `httpx`، `beautifulsoup4`، `pydantic>=2`، `telethon`، `pyyaml`، `geoip2` (موقعیت آفلاین)؛ آزمون با `pytest` + `pytest-asyncio`

**ذخیره‌سازی**: فایل `state/state.json` کامیت‌شده در مخزن (بدون پایگاه داده خارجی)

**آزمون**: `pytest`؛ آزمون واحد برای منطق خالص، آزمون یکپارچگی برای ارائه‌دهنده‌ها و خط لوله، آزمون قرارداد برای واسط‌ها

**پلتفرم هدف**: رانر `ubuntu-latest` در GitHub Actions؛ اجرای محلی با همان ورودی CLI

**نوع پروژه**: سرویس خودکار زمان‌بندی‌شده (نقطه ورود CLI برای CI)

**اهداف عملکردی**: اتمام چرخه کامل زیر ۳۰ دقیقه؛ سقف تست هر کانفیگ ۱۵ ثانیه (قابل تنظیم)؛ صفر تست تکراری برای کانفیگ یکتا

**محدودیت‌ها**: ممنوعیت ICMP (فقط تاخیر application-level)؛ فایل‌سیستم موقت رانر؛ اسرار فقط از محیط؛ هیچ secret در لاگ

**مقیاس/دامنه**: ده‌ها منبع، چند مقصد، صدها کانفیگ در هر اجرا

## معماری و کامپوننت‌ها

خط لوله در `pipeline.py` هماهنگ می‌شود و هر مرحله ماژول مستقل است:

1. **بارگذاری پیکربندی** (`config_loader`): اعتبارسنجی `config.yaml` + خواندن اسرار فقط از محیط؛ شکست یعنی توقف با پیام فارسی بدون secret.
2. **دریافت** (`providers`): به‌ازای هر منبع فعال، `fetch_new_posts(source, last_id)` با ارائه‌دهنده انتخابی (`auto` یعنی اسکرپ اول، Telethon در صورت شکست قابل تلاش)؛ خطای یک منبع، بقیه را متوقف نمی‌کند.
3. **تجزیه** (اقتباس `TelegramParser` مرجع): استخراج متن، زمان، رسانه؛ فیلتر پست سنجاق‌شده.
4. **استخراج** (`extraction`): یافتن همه لینک‌های کانفیگ در متن (چند کانفیگ در یک پست پشتیبانی می‌شود) + تشخیص پروتکل و اعتبارسنجی اولیه؛ اقلام بدقالب کنار گذاشته و شمارش می‌شوند.
5. **حذف تکراری** (`persistence` + حافظه): تطبیق دقیق رشته روی `raw` (مصوب Q5) **قبل** از هر کار پرهزینه.
6. **پاک‌سازی** (`filtering`): اعمال قوانین `exact` + `regex` (مصوب Q3) و افزودن نام کاربری مقصد طبق تنظیم.
7. **موقعیت** (`location`): GeoIP آفلاین؛ در صورت نبود پاسخ، مقدار جایگزین (FR-012)؛ خرابی موتور یعنی `fallback` نه توقف.
8. **تست** (`testing`): فقط کانفیگ‌های یکتای باقی‌مانده، یک‌بار سراسری (مصوب Q4) با سقف هم‌زمانی؛ خروجی `success`/`failed`/`timeout`/`skipped` + `latency_ms` غیرICMP.
9. **توزیع** (`distribution`): مسیریابی ناموفق‌ها به مقصد قرنطینه (FR-014) و بقیه با استراتژی پیکربندی‌شده (پیش‌فرض چرخشی، مصوب Q3) با مکان‌نمای پایدار.
10. **قالب‌بندی** (`formatting`): پیام هر مقصد با قالب مستقل خود (قرارداد `message-format`) بدون secret.
11. **ارسال** (`providers`): `BotApiSender` اول، `TelethonSender` در صورت فعال بودن fallback؛ محدودیت نرخ رعایت می‌شود.
12. **تداوم وضعیت** (`persistence`): به‌روزرسانی اتمیک `state/state.json` و کامیت در پایان چرخه موفق.
13. **گزارش** (`main` + `logging_setup`): شمارش هر مرحله (FR-031) در لاگ و خلاصه گردش کار.

## جریان داده

```text
Source → Fetch → Parse → Extract → Normalize → Deduplicate
  → Clean/filter → Detect location → Test → Measure latency
  → Distribute → Format → Send → Persist execution state
```

- انشعاب قرنطینه پس از Test رخ می‌دهد و به مرحله Distribute برمی‌گردد.
- هیچ مسیر بازگشتی به مراحل قبل از Deduplicate وجود ندارد (تضمین عدم تست تکراری).

## یکپارچگی‌های خارجی

| یکپارچگی | روش | نکته |
|----------|-----|------|
| پیش‌نمایش عمومی تلگرام | `https://t.me/s/...` با `httpx` (اقتباس مرجع) | بدون اعتبار؛ صفحه‌بندی `before`؛ پروکسی اختیاری |
| Bot API | HTTPS مستقیم `api.telegram.org` | `BOT_TOKEN` از Secret؛ تلاش مجدد محدود برای 429/5xx |
| Telethon | `API_ID`/`API_HASH`/`SESSION_STRING` از محیط | دریافت دوم و ارسال جایگزین؛ بدون لاگین تعاملی |
| Xray Core | باینری پین‌شده Releases + چک‌سام، اجرای زیرفرایند | inbound محلی + آزمون HTTP؛ جزئیات در [research.md](research.md) بخش ۴ و ۵ |
| GeoLite2 | دانلود در گردش کار با `MAXMIND_LICENSE_KEY` (Secret) + کش بین اجراها | آفلاین در زمان اجرا؛ در صورت نبود فایل پایگاه، موقعیت fallback بدون توقف (افت تدریجی) |
| GitHub | checkout، setup-python، cache، commit-state | امضای کامیت با `GITHUB_TOKEN` |

## امنیت

- اسرار (`BOT_TOKEN`، `API_ID`، `API_HASH`، `SESSION_STRING`) فقط از متغیر محیطی/GitHub Secrets خوانده می‌شوند؛ هیچ مقدار پیش‌فرض، لاگ، یا فایل نمونه حاوی secret واقعی نیست.
- لایه `logging_setup` همه مقادیر حساس را پیش از چاپ ماسک می‌کند؛ آزمون واحد专门 برای redaction وجود دارد.
- کمترین دسترسی: توکن بات فقط در چت‌های مقصد ادمین باشد؛ نشست Telethon جدا از حساب اصلی و قابل ابطال.
- باینری Xray با نسخه پین‌شده و راستی‌آزمایی چک‌سام دریافت می‌شود.

## راهبرد آزمون

- **واحد**: استخراج چند لینک از یک متن، تطبیق دقیق تکراری (با/بدون تفاوت فاصله)، قوانین exact/regex، توزیع چرخشی با مکان‌نما، قالب پیام، اعتبارسنجی پیکربندی، redaction لاگ.
- **یکپارچگی**: خط لوله MVP با فیکسچر DOM واقعی مرجع؛ تست+موقعیت با Xray واقعی در صورت دسترس بودن وگرنه `skipped`؛ ارسال خشک (dry-run) بدون شبکه.
- **قرارداد**: هر واسط با ارائه‌دهنده بدلی (fake) آزمون می‌شود تا تعویض پیاده‌سازی، قرارداد را نشکند.
- آستانه: پوشش کامل ماژول‌های خالص؛ هیچ PR بدون آزمون سبز ادغام نمی‌شود.

## استقرار و طراحی GitHub Actions

فایل `.github/workflows/forwarder.yml`:

- محرک‌ها: `schedule: cron '0 */3 * * *'` + `workflow_dispatch` (اجرای دستی با ورودی اختیاری مثل `--only-source`).
- `concurrency: group: forwarder / cancel-in-progress: false` (انحصار برای Idempotency).
- گام‌ها: checkout → setup-python 3.12 + cache pip → نصب وابستگی‌ها → دانلود Xray پین‌شده + چک‌سام (کش‌شده) → دانلود/کش پایگاه GeoIP → اجرای `python -m src.main --config config.yaml --once` → کامیت `state/state.json` در صورت تغییر → خلاصه اجرا (counts) در job summary.
- سیاست شکست: خطای مرحله پیکربندی/اسرار = fail؛ خطای جزئی منبع/کانفیگ = هشدار + ادامه؛ آستانه بحرانی (مثلاً همه منابع ناموفق) = fail با پیام فارسی.
- اسرار در `Settings → Secrets`: `BOT_TOKEN` (الزامی)، `API_ID`/`API_HASH`/`SESSION_STRING` (اختیاری، فقط برای مسیر دوم).

## تصمیم‌های معماری (خلاصه ADR)

- **ADR-1**: اسکرپ اول، Telethon دوم — دلیل: بدون اعتبار برای عمومی کافی است و با کمینه‌سازی اسرار سازگار است ([research ۱]).
- **ADR-2**: ارسال اصلی Bot API، جایگزین Telethon — دلیل: سادگی مسیر اصلی و پوشش خرابی با جایگزین ([research ۳]).
- **ADR-3**: Xray به‌صورت باینری پین‌شده + زیرفرایند — دلیل: سریع‌ترین نصب تکرارپذیر در CI ([research ۴]).
- **ADR-4**: تاخیر فقط application-level، هرگز ICMP — دلیل: مسدود بودن ICMP در رانرهای Azure ([research ۵]).
- **ADR-5**: وضعیت در خود مخزن — دلیل: سادگی و حسابرسی بدون سرویس خارجی در رانر موقت ([research ۶]).
- **ADR-6**: حذف تکراری دقیق قبل از تست + نتیجه مشترک — دلیل: حذف هزینه تست تکراری ([research ۱۰]، مصوب Q4/Q5).
- **ADR-7**: GeoIP آفلاین پیش‌فرض — دلیل: بدون وابستگی شبکه و بدون افشا ([research ۷]).
- **ADR-8**: ساختار تک‌پروژه Python ناهمگام — دلیل: هم‌خوانی با مرجع و ایزوله‌سازی خطا با حداقل پیچیدگی ([research ۹]).
