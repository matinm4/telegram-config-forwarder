# قانون اساسی سامانه خودکار جمع‌آوری و انتشار کانفیگ شبکه

> **قانون زبان (الزامی)**: تمام محتوای این فایل باید به **زبان فارسی** نوشته شود.

## اصول اصلی

### I. قابلیت اطمینان (اولویت P0)

سیستم MUST در برابر خطاهای موقت و جزئی مقاوم باشد و یک خطا در یک قلم داده، کل اجرا را متوقف نکند.

- سیستم MUST خطاهای موقت دریافت، دریافت ناقص پست یا رسانه، timeout، اختلال شبکه و خطای تست یک کانفیگ را به‌صورت ایزوله مدیریت کند.
- یک کانفیگ یا پست ناموفق MUST باعث حذف یا توقف پردازش سایر اقلام نشود.
- هر خطا MUST با زمینه کافی برای اشکال‌زدایی ثبت شود بدون افشای اسرار.
- منطق: قابلیت اطمینان پایه ارزش سیستم خودکار دوره‌ای است؛ توقف کامل به‌خاطر یک قلم، کل چرخه را بی‌اثر می‌کند.

### II. ماژولار بودن (اولویت P1)

مرز مسئولیت‌ها MUST شفاف و مستقل باشد.

- دریافت محتوا، استخراج کانفیگ، پردازش متن، تشخیص موقعیت، تست کانفیگ، توزیع بین مقصدها و ارسال MUST در ماژول‌های مستقل با واسط مشخص قرار گیرند.
- تغییر در یک ماژول SHOULD بدون تغییر در منطق کسب‌وکار ماژول‌های دیگر ممکن باشد.
- هر ماژول MUST به‌صورت مستقل قابل آزمون باشد.
- منطق: استقلال ماژول‌ها امکان جایگزینی ارائه‌دهنده، آزمون مستقل و توسعه برای تعداد زیاد منبع و مقصد را می‌دهد.

### III. پیکربندی‌پذیری (اولویت P1)

رفتار عادی سیستم MUST بدون تغییر کد منبع قابل تغییر باشد.

- تمام قابلیت‌های اختیاری شامل تشخیص موقعیت، تست کانفیگ، اندازه‌گیری تاخیر، چند مقصدی، روش توزیع، پالایش، قالب‌بندی، fallback و زمان‌بندی MUST از طریق پیکربندی قابل فعال‌سازی، غیرفعال‌سازی یا تنظیم باشند.
- تغییر رفتار عادی SHOULD نیاز به تغییر کد نداشته باشد؛ تغییر کد فقط برای رفتار جدید و غیرمنتظره مجاز است.
- مقادیر پیش‌فرض MUST صریح، مستند و امن باشند.
- منطق: پیکربندی‌پذیری هزینه بهره‌برداری را کم و خطر تغییر کد برای تنظیم روزمره را حذف می‌کند.

### IV. امنیت اسرار (اولویت P0، غیرقابل مذاکره)

هیچ داده حساسی MUST در مخزن قرار نگیرد.

- توکن‌ها، شناسه‌ها، هش‌ها، رشته‌های نشست و سایر اسرار MUST فقط از GitHub Secrets یا سازوکار امن معادل خوانده شوند.
- اسرار MUST در کد، پیکربندی نسخه‌شده، مستندات یا تاریخچه مخزن ذخیره نشوند.
- دسترسی به اسرار MUST به حداقل لازم محدود باشد.
- منطق: افشای اعتبار، کل سیستم و کانال‌ها را به خطر می‌اندازد و جبران آن پرهزینه است.

### V. مشاهده‌پذیری (اولویت P1)

هر اجرا MUST قابل مشاهده و اشکال‌زدایی باشد.

- تعداد پست‌های دریافتی، کانفیگ‌های استخراج‌شده، تست‌شده، ناموفق و ارسال‌های موفق MUST در خروجی اجرا قابل مشاهده باشند.
- خطاها MUST با دسته‌بندی، شمارش و زمینه کافی ثبت شوند.
- وضعیت اجرای زمان‌بندی‌شده و دستی MUST قابل تمایز باشد.
- منطق: بدون مشاهده‌پذیری، تشخیص افت کیفیت منابع، خرابی ارائه‌دهنده یا خطای توزیع ممکن نیست.

### VI. آزمون‌پذیری (اولویت P1)

منطق اصلی MUST قابل آزمون خودکار باشد.

- منطق خالص شامل استخراج، نرمال‌سازی، حذف تکراری، پالایش متن، توزیع و قالب‌بندی MUST با آزمون واحد پوشش داده شود.
- تعامل‌های مهم بیرونی MUST با آزمون یکپارچگی پوشش داده شوند.
- آزمون‌ها SHOULD بدون نیاز به اعتبار واقعی یا شبکه زنده تا حد امکان اجراشونده باشند.
- منطق: آزمون‌پذیری، تنها راه مطمئن شدن از صحت تغییرات در خط لوله چندمرحله‌ای است.

### VII. تحمل خطا و fallback (اولویت P1)

برای مسیرهای حیاتی دریافت و ارسال SHOULD مسیر جایگزین وجود داشته باشد.

- اگر روش اصلی دریافت یا ارسال دچار خطا شد، سیستم SHOULD در صورت امکان و طبق پیکربندی از روش fallback استفاده کند.
- انتخاب ارائه‌دهنده MUST از طریق واسط صورت گیرد تا تعویض ارائه‌دهنده نیاز به تغییر منطق کسب‌وکار نداشته باشد.
- فعال یا غیرفعال بودن fallback و شرایط آن MUST در پیکربندی مشخص باشد.
- منطق: وابستگی به یک مسیر واحد، نقطه شکست واحد ایجاد می‌کند.

### VIII. تکرارپذیری امن یا Idempotency (اولویت P0)

اجرای مجدد MUST اثر جانبی تکراری ایجاد نکند.

- اجرای مجدد گردش کار MUST باعث انتشار تکراری بی‌دلیل کانفیگ یا پست نشود.
- تشخیص تکراری‌بودن پست و کانفیگ MUST قطعی و پایدار بین اجراها باشد.
- وضعیت توزیع بین مقصدها MUST به‌گونه‌ای نگهداری شود که تکرار اجرا، توزیع را به‌هم نریزد.
- منطق: اجرای زمان‌بندی‌شده ذاتا تکراری است؛ بدون Idempotency، هر تلاش مجدد باعث اسپم می‌شود.

### IX. نگهداشت‌پذیری (اولویت P2)

مخزن MUST واضح، مستند و قابل توسعه بماند.

- ساختار مخزن MUST برای افزودن منبع و مقصد جدید بدون بازطراحی مقیاس‌پذیر باشد.
- هر ماژول SHOULD یک مسئولیت واحد و قرارداد ورودی و خروجی مشخص داشته باشد.
- پیچیدگی جدید MUST توجیه شود و جایگزین ساده‌تر آن ردشده و مستند باشد.
- منطق: تعداد منابع و مقصدها رشد می‌کند؛ ساختار نامشخص هزینه توسعه را نمایی می‌کند.

### X. مستندسازی (اولویت P1)

پیکربندی و رفتار MUST مستند باشند.

- راهنمای کامل فارسی مدیریت پیکربندی MUST وجود داشته باشد و هر گزینه، اثر و نحوه تغییر آن را توضیح دهد.
- فایل README مخزن MUST دوزبانه فارسی و انگلیسی باشد.
- رفتار fallback، مقادیر پیش‌فرض و محدودیت‌های شناخته‌شده MUST مستند باشند.
- منطق: بیشتر تغییرات بهره‌برداری در لایه پیکربندی است؛ بدون مستند فارسی دقیق، خطای انسانی اجتناب‌ناپذیر است.

### XI. اولویت GitHub Actions (اولویت P0)

اجرای تولید MUST بدون وابستگی به رایانه شخصی ممکن باشد.

- اجرای اصلی تولید MUST به‌صورت کامل در GitHub Actions انجام شود.
- گردش کار MUST هم زمان‌بندی‌شده و هم قابل اجرای دستی باشد.
- اجرای زمان‌بندی‌شده پیش‌فرض هر ۳ ساعت یک‌بار است مگر در پیکربندی خلاف آن تعیین شود.
- گردش کار MUST در برابر خرابی‌های جزئی مقاوم باشد و خرابی یک قلم، کل اجرا را ناموفق اعلام نکند مگر آستانه تعیین‌شده رد شود.
- منطق: وابستگی به سیستم شخصی، دسترس‌پذیری و تکرارپذیری را از بین می‌برد.

### XII. افت تدریجی یا Graceful Degradation (اولویت P1)

ازکارافتادن یک قابلیت اختیاری MUST کل خط لوله را متوقف نکند.

- اگر تشخیص موقعیت یا تست اتصال موقتا قابل اجرا نبود، سیستم MUST طبق رفتار fallback پیکربندی‌شده ادامه دهد و توقف بی‌دلیل ممنوع است.
- رفتار fallback هر قابلیت اختیاری MUST صریح و قابل تنظیم باشد.
- هر افت تدریجی MUST در خروجی و لاگ مشخص باشد تا از موفقیت کامل متمایز شود.
- منطق: قابلیت‌های کمکی نباید به گلوگاه حیاتی تبدیل شوند.

### XIII. حریم خصوصی لاگ‌ها (اولویت P0، غیرقابل مذاکره)

لاگ‌ها MUST عاری از داده حساس باشند.

- اعتبارها، اسرار، توکن‌ها و داده‌های حساس MUST هرگز در لاگ، خروجی گردش کار یا پیام خطا چاپ نشوند.
- خطاهای مرتبط با احراز هویت MUST بدون افشای مقدار secret ثبت شوند.
- هرگونه نقض این اصل، تخلف بحرانی محسوب می‌شود و MUST قبل از انتشار رفع شود.
- منطق: لاگ‌ها پرتکرارترین محل نشت تصادفی اسرار هستند.

## محدودیت‌های اضافی

این بخش قواعد مکمل الزام‌آور است و بر همه تصمیم‌های طراحی و پیاده‌سازی ارجح است.

- اسرار فقط از منبع امن خوانده می‌شوند؛ هیچ استثنایی برای راحتی توسعه یا آزمون تولیدی مجاز نیست.
- انتشار تکراری ممنوع است مگر کاربر صراحتا و آگاهانه آن را درخواست کرده باشد.
- توقف کامل خط لوله به‌خاطر خرابی یک قابلیت اختیاری ممنوع است.
- هر رفتار اختیاری که اثر کاربری دارد MUST کلید پیکربندی صریح و مقدار پیش‌فرض مستند داشته باشد.
- مستند فارسی پیکربندی و README دوزبانه، شرط پذیرش انتشار هستند نه تزئین اختیاری.

## گردش کار توسعه و دروازه‌های کیفیت

- هر تغییر رفتار MUST ابتدا در مشخصات، سپس در طرح و سپس در وظایف منعکس شود؛ پیاده‌سازی مستقیم بدون ردیابی مشخصات ممنوع است.
- هر طرح MUST بررسی قانون اساسی را قبل از تحقیق و بعد از طراحی پاس کند؛ تخلف توجیه‌نشده، خطای مسدودکننده است.
- هر بازبینی MUST انطباق با این قانون اساسی را تایید کند.
- آزمون خودکار برای منطق اصلی الزامی است؛ ادعای صحت بدون آزمون پذیرفته نیست.
- پیچیدگی جدید بدون توجیه مستند، مردود است.

## حکمرانی

این قانون اساسی بر تمام رویه‌ها، مشخصات، طرح‌ها و پیاده‌سازی‌ها ارجح است. در تعارض، قانون اساسی حاکم است نه سند جزئی‌تر.

- اصلاح این سند فقط با مستندسازی دلیل، ثبت در گزارش اثر همگام‌سازی و بازبینی انسانی مجاز است.
- نسخه‌گذاری معنایی الزامی است: MAJOR برای حذف یا بازتعریف ناسازگار اصول، MINOR برای افزودن اصل یا بخش جدید یا توسعه مادی راهنما، PATCH برای شفاف‌سازی، اصلاح نگارش و پالایش غیرمعنایی.
- تاریخ‌ها با قالب ISO به‌صورت YYYY-MM-DD ثبت می‌شوند.
- هر اصلاح MUST نسخه، تاریخ آخرین اصلاح و خلاصه تغییر را به‌روز کند.
- انطباق در هر درخواست تغییر بررسی می‌شود؛ تخلف از اصول P0 MUST مانع انتشار شود.
